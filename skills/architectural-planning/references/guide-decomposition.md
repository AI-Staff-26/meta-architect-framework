# 🧩 Decomposition — Декомпозиция Задач

<purpose>
Большие задачи ломают LLM. Маленькие задачи = предсказуемый результат.
</purpose>

---

## Ключевые Принципы

### 1. Правило Одного Экрана

> **Одна задача = один экран кода изменений (50-100 строк).**

```
❌ Плохо:
"Реализуй систему авторизации с JWT, ролями и OAuth."

✅ Хорошо:
1. "Создай модель User с полями email, passwordHash."
2. "Добавь endpoint POST /auth/login с JWT."
3. "Добавь middleware для проверки токена."
4. "Добавь роли и проверку ролей в middleware."
```

**Правило:** Если задача требует изменения >3 файлов — декомпозируй.

---

### 2. Вертикальная Декомпозиция (Vertical Slice)

> **Режь по фичам, не по слоям.**

```
❌ Плохо (горизонтально):
1. Создай все модели
2. Создай все репозитории
3. Создай все сервисы
4. Создай все контроллеры

✅ Хорошо (вертикально):
1. Фича "Создание пользователя" (модель → репо → сервис → контроллер)
2. Фича "Аутентификация" (полный слайс)
3. Фича "Профиль" (полный слайс)
```

**Почему вертикально лучше:**
- Каждый слайс можно проверить end-to-end
- Меньше зависимостей между задачами
- Легче откатить при ошибке
- @coder видит полный контекст фичи

---

### 3. Правило Зависимостей

> **Выполняй задачи в порядке зависимостей. Никаких forward references.**

```markdown
## Граф зависимостей:

[Модель User] ─────┐
                   ├──→ [Auth Service] ──→ [Auth Controller]
[JWT Config] ──────┘

[Auth Middleware] ←── [Auth Service]

Порядок:
1. Модель User
2. JWT Config
3. Auth Service
4. Auth Middleware
5. Auth Controller
```

**Правило:** Перед задачей убедись, что все зависимости уже реализованы.

---

### 4. Атомарность Задачи

> **Одна задача = одно изменение = один коммит.**

**Критерии атомарности:**
| Критерий | Описание |
|----------|----------|
| Компилируется | После задачи проект собирается |
| Тестируется | Можно написать изолированный тест |
| Откатывается | git revert без побочных эффектов |
| Описывается | Умещается в 1 предложение |

**Пример атомарной задачи:**
```
✅ "Добавить валидацию email в UserService.register()"

- Изменяет 1 файл (UserService)
- Добавляет 10-20 строк
- Можно протестировать изолированно
- Revert не сломает другие части
```

---

### 5. Уровни Декомпозиции

```
Уровень 0: Epic (эпик)
└── "Система авторизации"

Уровень 1: Feature (фича)
├── "Регистрация пользователя"
├── "Аутентификация по JWT"
└── "Управление сессиями"

Уровень 2: Story (история)
├── "Создание пользователя в БД"
├── "Хеширование пароля"
└── "Валидация email"

Уровень 3: Task (задача для @coder)
├── "Добавить поле email в модель User"
├── "Реализовать hashPassword() в UserService"
└── "Добавить EmailValidator с regex"
```

**Для @coder:** Отправляй только Уровень 3 (Task).

## Алгоритм Декомпозиции

### Шаг 1: Определи Границы

```markdown
Вопросы:
- Какие сущности затронуты?
- Какие слои архитектуры?
- Какие внешние зависимости?
- Где точки интеграции?
```

### Шаг 2: Построй Граф Зависимостей

```markdown
Для каждой части:
- Что должно существовать ДО этой части?
- Что зависит ОТ этой части?
- Есть ли циклические зависимости? (разорви их)
```

### Шаг 3: Разбей на Вертикальные Слайсы

```markdown
Для каждого слайса:
- Есть ли начало (input)?
- Есть ли конец (output)?
- Можно ли проверить изолированно?
```

### Шаг 4: Упорядочи по Зависимостям

```markdown
Правила:
1. Модели → перед сервисами
2. Утилиты → перед использующим кодом
3. Интерфейсы → перед реализациями
4. Core → перед features
```

### Шаг 5: Сформируй Задачи для @coder

```markdown
Каждая задача включает:
- Что сделать (1 предложение)
- Где сделать (конкретный файл/модуль)
- Acceptance Criteria (как проверить)
- Связь с предыдущей/следующей задачей
```

## Антипаттерны

| Антипаттерн | Признак | Как исправить |
|-------------|---------|---------------|
| **Big Bang** | "Реализуй всё" | Декомпозируй на слайсы |
| **Layer Cake** | Все модели, потом все сервисы | Вертикальные слайсы |
| **Hidden Dependency** | "Почему не работает?" | Построй граф зависимостей |
| **Mega Task** | >100 строк изменений | Разбей на атомы |
| **Forward Reference** | "Используй сервис, который будет позже" | Реорганизуй порядок |
| **Fuzzy Scope** | "Примерно сделай" | Конкретные Acceptance Criteria |

## Шаблон Декомпозиции

```markdown
# Декомпозиция: [Название фичи]

## Обзор
[1-2 предложения: что делаем]

## Зависимости
- Внешние: [библиотеки, сервисы]
- Внутренние: [существующие модули]

## Задачи

### 1. [Название задачи]
- **Файл:** `path/to/file.ts`
- **Действие:** [что сделать]
- **AC:** [как проверить]
- **Depends on:** [предыдущая задача или -]

### 2. [Название задачи]
...

## Граф зависимостей
[ASCII или Mermaid диаграмма]

## Проверка
[Как проверить всю фичу end-to-end]
```

## Quick Reference

```
Декомпозиция = Контроль сложности

Правила:
1. 1 задача = 1 экран (50-100 строк)
2. Вертикальные слайсы > горизонтальные слои
3. Зависимости → определяют порядок
4. Атомарность → компилируется, тестируется, откатывается
5. Уровень 3 (Task) → для @coder
```
