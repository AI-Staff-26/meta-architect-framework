# ✍️ Prompt Engineering — Как Писать Сильные Промпты

<purpose>
Качество промпта определяет качество результата. Garbage In = Garbage Out.
</purpose>

---

## Анатомия Сильного Промпта

### Базовая Структура

```markdown
# Task: [Конкретное название]

## Context
[Почему это важно, как вписывается в систему]

## Scope
[Точные шаги. Что делать, что НЕ делать]

## Requirements
1. [Измеримое требование]
2. [Измеримое требование]

## Constraints (❌ Чего НЕ делать)
❌ [Явный запрет 1]
❌ [Явный запрет 2]

## Acceptance Criteria
✅ [Как проверить успех]
✅ [Конкретная метрика]

## Files to Work With
- `path/to/file.ts` — [что изменить]

## Output Format
[Код / Отчёт / Анализ]
```

---

## Ключевые Техники

### 1. Chain of Thought (Цепочка Рассуждений)

> **Позволь модели "думать вслух" для сложных задач.**

```markdown
❌ Плохо:
"Реализуй авторизацию"

✅ Хорошо:
"Реализуй авторизацию:
1. Сначала определи, какие endpoints требуют защиты
2. Затем выбери стратегию (JWT/Session)
3. Реализуй middleware проверки
4. Добавь обработку ошибок (401, 403)
5. Напиши тесты"
```

**Когда использовать:** 🟡🔴 задачи, многошаговая логика.

---

### 2. Few-Shot (Примеры)

> **Покажи пример желаемого результата.**

```markdown
❌ Плохо:
"Напиши сервис как в проекте"

✅ Хорошо:
"Напиши сервис по образцу UserService:

\```typescript
// Пример: UserService
@Injectable()
export class UserService {
  constructor(private readonly repo: UserRepository) {}
  
  async findById(id: string): Promise<User> {
    const user = await this.repo.findOne(id);
    if (!user) throw new NotFoundException();
    return user;
  }
}
\```

Создай аналогичный ProductService с методами:
- findById
- findAll
- create"
```

**Когда использовать:** Когда важен стиль/формат кода.

---

### 3. Persona Pattern (Роль)

> **Определи роль для фокусировки поведения.**

```markdown
❌ Плохо:
"Проанализируй код"

✅ Хорошо:
"Ты — Senior Security Engineer.
Проведи аудит этого кода:
- Найди уязвимости (injection, XSS, IDOR)
- Проверь валидацию входных данных
- Оцени работу с секретами"
```

**Когда использовать:** Специализированные задачи (security, performance, legacy).

---

### 4. Negative Constraints (Явные Запреты)

> **Модели лучше следуют явным запретам, чем неявным ожиданиям.**

```markdown
❌ Плохо:
"Пиши чистый код"

✅ Хорошо:
"## Constraints
❌ НЕ используй `any` в TypeScript
❌ НЕ добавляй console.log (используй logger)
❌ НЕ меняй существующие API контракты
❌ НЕ добавляй новые зависимости
❌ НЕ коммить .env или секреты"
```

**Правило:** Минимум 3-5 явных ❌ в каждом промпте для `code`.

---

### 5. Measurable Criteria (Измеримые Критерии)

> **Критерии должны быть проверяемыми, не субъективными.**

```markdown
❌ Плохо:
- "Должно работать быстро"
- "Код должен быть чистым"
- "Покрыть тестами"

✅ Хорошо:
- "Response time p95 < 200ms"
- "Все публичные методы документированы JSDoc"
- "Test coverage > 80% для новых файлов"
- "Все тесты проходят: `npm test`"
- "Lint без ошибок: `npm run lint`"
```

---

### 6. Context Priming (Подготовка Контекста)

> **Дай модели необходимый контекст ДО задачи.**

```markdown
❌ Плохо:
"Добавь валидацию в форму"

✅ Хорошо:
"## Context
Проект использует:
- React Hook Form для форм
- Zod для валидации схем
- Существующие паттерны в `src/components/forms/`

## Task
Добавь валидацию в форму регистрации:
- Email: формат + уникальность
- Password: минимум 8 символов, 1 цифра
- Паттерн ошибок как в LoginForm"
```

## Антипаттерны

| Антипаттерн | Пример | Проблема | Исправление |
|-------------|--------|----------|-------------|
| **Vague Scope** | "Улучши код" | Нет критериев | Конкретные метрики |
| **No Constraints** | Промпт без ❌ | Модель делает лишнее | Добавить 3-5 запретов |
| **Implicit Expectations** | "Как обычно" | Модель не знает "обычно" | Явные примеры |
| **Wall of Text** | 2000 слов | Lost in the Middle | Структура, важное в начало/конец |
| **Hope-driven Prompts** | "Надеюсь поймёт" | Не поймёт | Быть explicit |

## Итеративное Уточнение (Refinement)

> **Первый промпт редко идеален. Уточняй на основе результата.**

```
Цикл:
1. Промпт v1 → Результат
2. Анализ: что не так?
3. Добавить constraint/example/clarification
4. Промпт v2 → Результат
5. Повторять до качества
```

**Важно:** Каждое уточнение должно быть ДОБАВЛЕНИЕМ, не переписыванием с нуля.

---

## Self-Consistency Check

> **Для критичных задач — проверь через альтернативный подход.**

```markdown
"Проверь своё решение:
1. Пройди по каждому требованию — выполнено?
2. Проверь каждый ❌ constraint — не нарушен?
3. Запусти мысленно edge cases — обработаны?
4. Если нашёл проблему — исправь ДО ответа"
```

## 7. Lettered Options (Быстрые Итерации)

> **Ускорь сбор требований через варианты ответов.**

```markdown
❌ Плохо:
"Какой frontend фреймворк использовать?"

✅ Хорошо:
"1. Какой frontend фреймворк предпочтителен?
   A. React (экосистема, найм)
   B. Vue (простота, скорость)
   C. Angular (enterprise, TypeScript)
   D. Другой: [specify]"
```

**Пользователь отвечает:** `1A, 2C, 3B` — максимально быстрая итерация.

**Когда использовать:** Сбор требований, уточняющие вопросы, выбор технологий.

## 8. Writing for Junior Developers (Ясность)

> **Читатель промпта может быть junior developer или AI agent.**

```markdown
❌ Плохо:
"Реализуй как обычно с DI и паттерном Repository"

✅ Хорошо:
"Реализуй сервис по следующему паттерну:
1. Создай класс UserService с конструктором, принимающим UserRepository
2. Метод findById должен:
   - Принять id: string
   - Вызвать this.repo.findOne(id)
   - Выбросить NotFoundException если user не найден
   - Вернуть User

Пример:
\\```typescript
async findById(id: string): Promise<User> {
  const user = await this.repo.findOne(id);
  if (!user) throw new NotFoundException();
  return user;
}
\\```"
```

**Принципы:**

- Будь **explicit и unambiguous** — никаких неявных ожиданий
- **Избегай жаргона** или объясняй его
- **Нумеруй шаги** для удобства ссылок
- **Давай примеры** где это помогает пониманию
- Критерии должны быть **verifiable**:
  - ❌ «Works correctly»
  - ✅ «Button shows confirmation dialog before deleting»
