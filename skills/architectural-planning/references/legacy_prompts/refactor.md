# ♻️ `code` Prompt — Refactor

<purpose>
Шаблон промпта для делегирования задачи рефакторинга агенту `code`.
Рефакторинг = изменение структуры кода БЕЗ изменения поведения.
</purpose>

---

## Когда Использовать

**Подходит для:**
- Улучшение читаемости кода
- Устранение дублирования (DRY)
- Разделение ответственности (SRP)
- Переименование / реорганизация
- Оптимизация производительности (без изменения API)
- Применение паттернов

**НЕ использовать для:**
- Добавления новой функциональности → `implement.md`
- Фикса багов → `fix-bug.md`
- Breaking changes в API

---

## Template

```markdown
# Task: Refactor [Что именно рефакторим]

## Context
[Почему нужен рефакторинг. Какая проблема решается.]

**Текущее состояние:**
[Описание текущих проблем: дублирование, сложность, нарушение принципов]

**Целевое состояние:**
[Как должно выглядеть после рефакторинга]

## Scope
[Точные шаги рефакторинга. Ничего лишнего.]

1. [Шаг 1]
2. [Шаг 2]
3. [Шаг 3]

## Refactoring Type
[Укажи тип рефакторинга]

- [ ] Extract Method / Function
- [ ] Extract Class / Module
- [ ] Rename
- [ ] Move
- [ ] Inline
- [ ] Replace Conditional with Polymorphism
- [ ] Introduce Parameter Object
- [ ] Other: [опиши]

## Constraints (Критически важно!)
⚠️ **ПОВЕДЕНИЕ НЕ ДОЛЖНО ИЗМЕНИТЬСЯ**
❌ Не менять публичный API / контракты
❌ Не добавлять новую функциональность
❌ Не удалять функциональность
❌ Не менять тесты (кроме адаптации к новой структуре)
❌ Не оптимизировать "заодно" другие места

## Acceptance Criteria
✅ Все существующие тесты проходят БЕЗ ИЗМЕНЕНИЙ логики
✅ Build чистый
✅ Lint чистый
✅ [Конкретная метрика: меньше строк / классов / дублирования]
✅ Код соответствует целевому состоянию

## Files to Work With
| File | Action | Description |
|------|--------|-------------|
| `path/to/file.ts` | MODIFY | Что извлекаем |
| `path/to/new-file.ts` | CREATE | Куда извлекаем |

## Verification
[Как убедиться, что поведение не изменилось]

1. Все тесты проходят
2. [Конкретный ручной тест если нужен]
3. [Сравнение output до/после если применимо]

## Output Format
Только код.
Отчёт после завершения:
- Что изменено
- Какие файлы затронуты
- Тесты проходят (да/нет)
```

## Примеры Заполнения

### Extract Function

```markdown
# Task: Refactor — Extract validation logic from UserController

## Context
Метод `createUser` в UserController содержит 50+ строк валидации,
смешанной с бизнес-логикой. Нарушает SRP.

**Текущее состояние:**
- Валидация inline в контроллере
- Дублируется в `updateUser`
- Сложно тестировать отдельно

**Целевое состояние:**
- Валидация в отдельном `UserValidator` классе
- Переиспользуется в обоих методах
- Легко тестировать

## Scope
1. Создать `UserValidator` класс
2. Извлечь валидацию из `createUser`
3. Извлечь валидацию из `updateUser`
4. Заменить inline-валидацию вызовом validator

## Refactoring Type
- [x] Extract Class / Module

## Constraints
⚠️ Поведение НЕ должно измениться!
❌ Не менять ошибки валидации (те же коды, те же сообщения)
❌ Не добавлять новые проверки
❌ Не менять порядок проверок

## Acceptance Criteria
✅ Все тесты UserController проходят
✅ Новый UserValidator покрыт unit тестами
✅ Дублирование устранено
✅ createUser < 20 строк

## Files to Work With
| File | Action | Description |
|------|--------|-------------|
| `src/validators/UserValidator.ts` | CREATE | Извлечённая логика |
| `src/controllers/UserController.ts` | MODIFY | Убрать inline валидацию |
| `tests/validators/UserValidator.test.ts` | CREATE | Unit тесты |

## Verification
1. Все 15 тестов UserController проходят
2. Ошибки валидации идентичны (сравнить response)
```

### Rename / Reorganize

```markdown
# Task: Refactor — Rename and reorganize utils

## Context
Папка `/utils` превратилась в свалку из 30+ файлов без структуры.
Нужна категоризация.

**Текущее состояние:**
- `/utils/` — плоская структура, 30+ файлов
- Имена неконсистентны (helpers.ts, utils.ts, misc.ts)

**Целевое состояние:**
- `/utils/string/` — работа со строками
- `/utils/date/` — работа с датами
- `/utils/array/` — работа с массивами
- `/utils/http/` — HTTP helpers

## Scope
1. Создать подпапки
2. Переместить файлы по категориям
3. Обновить все импорты
4. Удалить пустые old files

## Refactoring Type
- [x] Move
- [x] Rename

## Constraints
⚠️ Поведение НЕ должно измениться!
❌ Не менять содержимое функций
❌ Не удалять функции
❌ Не объединять файлы

## Acceptance Criteria
✅ Все тесты проходят
✅ Все импорты обновлены
✅ Нет broken references
✅ Структура соответствует плану

## Files to Work With
[Список всех файлов для перемещения с указанием откуда → куда]
```

## Чеклист перед Отправкой

- [ ] Тип рефакторинга указан
- [ ] Текущее состояние описано (что плохо)
- [ ] Целевое состояние описано (что хотим)
- [ ] Constraints подчёркивают: ПОВЕДЕНИЕ НЕ МЕНЯЕТСЯ
- [ ] Verification описывает как проверить
- [ ] Нет скрытых новых фич

---

## ⚠️ Важные Напоминания

1. **Тесты — индикатор успеха.** Если тесты падают после рефакторинга
   (и не из-за переименования), что-то пошло не так.

2. **Маленькие шаги.** Лучше 5 маленьких рефакторингов, чем 1 огромный.

3. **Один тип за раз.** Не смешивай Extract + Rename + Optimize в одной задаче.
